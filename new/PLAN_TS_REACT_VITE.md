# План переписывания приложения на TypeScript + React + Vite

> **Checkpoint 2026-09-08:** новый React-интерфейс, static data source, расписания студентов и преподавателей, кэш, platform layer, responsive/pastel UI, favicon, lucide-иконки и unit/lint checks реализованы. Последний завершённый шаг: адаптивный mobile selector и финальная проверка `lint` / `test` / `typecheck` / `build`. Следующее продолжение: CI/деплой Vite на GitHub Pages, затем регрессионная проверка и перенос legacy frontend в `legacy/`. Legacy-файлы пока остаются в корне. Локальный набор данных содержит `data/meta.json`, каталоги и студенческие месячные файлы; `data/t/` ещё отсутствует.

## 1. Цель и ограничения

Переписать текущий статический SPA для расписания КГУ на TypeScript, React и Vite, сохранив пользовательские возможности:

- расписание студентов и преподавателей;
- выбор факультета, курса, группы, кафедры и преподавателя;
- поиск;
- навигацию по неделям;
- сохранённые группы;
- кэш расписаний и работу без сети для ранее загруженных данных;
- запуск в обычном браузере и Telegram Mini App;
- текущий вариант предварительно загруженных JSON-файлов.

В будущем приложение должно уметь получать те же данные через API. API-модуль на этом этапе не реализуется: необходимо только заложить стабильный контракт и точку подключения.

Токены и приватные параметры API не должны попадать в клиентский код.

## 2. Текущее поведение, которое нужно сохранить

1. `scripts/fetch_data.py` получает каталоги и месячные расписания, сохраняет их в `data/`.
2. Клиент загружает `meta.json`, `students.json`, `teachers.json` и файлы расписаний по месяцам.
3. Студенты и преподаватели загружаются лениво при открытии соответствующей вкладки.
4. Выбранные сущности и сохранённые группы лежат в `localStorage`.
5. Telegram определяется через WebApp API; браузерный режим остаётся отдельным вариантом платформы.
6. Отсутствие свежих файлов не должно ломать просмотр ранее закэшированных расписаний.
7. Формат и семантика расписания после загрузки проходят через общий парсер и объединение данных по месяцам.

Перед началом миграции зафиксировать эти сценарии как ручной чек-лист регрессии.

```text

  app/
    App.tsx                # корневой компонент и маршрутизация вкладок
    app.css                # глобальные стили и Telegram-переменные
    config.ts              # runtime-конфигурация и базовые URL
  components/
    layout/

      studentSelectors.ts
    teachers/

      teacherSelectors.ts
    schedule/
      scheduleSelectors.ts
  data/
    types.ts               # доменные типы и DTO источников
    dataSource.ts          # интерфейс источника данных
    staticDataSource.ts    # чтение текущих JSON-файлов
    apiDataSource.ts       # будущий API-адаптер, пока заглушка/задача
    normalize.ts            # преобразование внешнего формата в доменный
  platform/
    platform.ts            # browser/Telegram abstraction
    telegram.ts

    scheduleCache.ts
  lib/
```

Названия можно адаптировать под выбранную библиотеку управления состоянием. На старте не добавлять state-management библиотеку без необходимости: React state + Context или существующая небольшая библиотека должны покрыть сценарии, пока не появится подтверждённая сложность.

## 4. Главный архитектурный контракт

UI и feature-логика не должны знать, загружены данные из JSON или получены из API. Оба источника должны реализовать один интерфейс примерно такого вида:

```ts
export type ScheduleKind = 'student' | 'teacher';

export interface ScheduleDataSource {
  getMeta(): Promise<ScheduleMeta>;
  getStudentCatalog(): Promise<StudentCatalog>;
  getTeacherCatalog(): Promise<TeacherCatalog>;
  getSchedule(
    kind: ScheduleKind,
    entityId: string,
    period: SchedulePeriod,
  ): Promise<RawSchedule>;
}
```

Точные типы определить после инвентаризации реальных JSON и ответов API. Контракт должен включать:

- каталог студентов;
- каталог преподавателей;
- доступные периоды;
- расписание конкретной группы или преподавателя;
- единый формат ошибок и отсутствие данных;
- метаданные актуальности, если источник их предоставляет.

Выбор источника выполнять через конфигурацию приложения или фабрику:

```ts
const dataSource = createDataSource({ mode: 'static' });
```

Позже переключение на API должно менять только конфигурацию и реализацию `apiDataSource`, а не компоненты расписания.

## 5. Пошаговый план

### Шаг 1. Зафиксировать исходные контракты и сценарии

- Составить таблицу всех используемых JSON: путь, обязательные поля, пример значения, потребитель.
- Отдельно описать формат `meta.json`, `students.json`, `teachers.json` и месячных файлов `data/s/...` и `data/t/...`.
- Зафиксировать существующие ключи `localStorage`: активная вкладка, выбранная группа, выбранный преподаватель, сохранённые группы, кэш расписания.
- Проверить сценарии в browser и Telegram.
- Определить минимальный набор ручных проверок для каждой вкладки.

**Результат:** согласованный доменный словарь и список регрессионных сценариев.

### Шаг 2. Подготовить Vite-проект в отдельной ветке/папке

- Добавить `package.json`, TypeScript-конфигурацию и Vite-конфигурацию.
- Настроить команды `dev`, `build`, `preview`, `typecheck` и `lint`.
- Подключить React и React DOM.
- Настроить алиасы импортов только при реальной пользе.
- Перенести текущий `styles.css` без массового редизайна.
- Настроить `base` для GitHub Pages, если приложение деплоится в подпуть репозитория.
- Оставить `scripts/fetch_data.py` источником статических данных.

**Проверка:** чистый `npm run build` на пустом стартовом экране.

### Шаг 3. Описать типы домена

Создать типы для:

- факультета/кафедры;
- курса и группы;
- преподавателя;
- месяца/периода;
- занятия, дня и нормализованного расписания;
- сохранённой группы;
- состояния загрузки, ошибки и кэшированной версии.

Разделить внешние DTO и внутренние доменные модели. Компоненты React должны получать доменные модели, а не повторять структуру API или JSON.

**Проверка:** `tsc --noEmit` не допускает `any` в публичных контрактах источника данных.

### Шаг 4. Реализовать статический источник данных

- Перенести логику `fetchJSON` в `staticDataSource.ts`.
- Сохранить текущие пути к `data/` и загрузку `meta.json`.
- Реализовать запрос месячного расписания через тот же метод `getSchedule`.
- Добавить нормализацию JSON в доменный формат.
- Ошибки сети, HTTP и отсутствующие файлы привести к единому типу ошибки.
- API не вызывать из браузера и не переносить токены из Python-скрипта.

**Проверка:** приложение работает с теми же файлами `data/`, что и текущая версия.

### Шаг 5. Перенести storage и кэш

- Сделать типизированную обёртку над `localStorage`.
- Сохранить совместимость с существующими ключами, чтобы пользователи не потеряли настройки после деплоя.
- Вынести формат кэша и TTL/время сохранения в `scheduleCache.ts`.
- Описать стратегию: сначала сеть/статический источник, затем кэш при ошибке; для сохранённых групп разрешить восстановление без каталога.
- Обработать недоступный или переполненный `localStorage` без падения приложения.

**Проверка:** выбор группы, сохранение, удаление и восстановление после перезагрузки работают как раньше.

### Шаг 6. Перенести платформенный слой

- Оставить единый интерфейс для browser и Telegram: `ready`, back button, safe area, тема, fullscreen/expand.
- Убрать прямые обращения компонентов к `window.Telegram`.
- Передавать платформу через `PlatformProvider` или сервисный объект.
- Сохранить классы/переменные темы Telegram и поведение кнопки «назад».
- Не считать Telegram API обязательным для локальной разработки.

**Проверка:** browser не падает при отсутствии Telegram SDK; Mini App сохраняет текущую адаптацию.

### Шаг 7. Перенести экран приложения и вкладки

- Создать `App.tsx` с вкладками студентов и преподавателей.
- Перенести hash-навигацию или заменить её на лёгкий роутер, сохранив URL-ссылки `#students` и `#teachers`, если они используются.
- Сохранить ленивую загрузку каталогов по вкладке.
- Для асинхронных операций явно обработать `loading`, `error`, `empty` и `success`.
- Не смешивать получение данных, бизнес-логику выбора и JSX-рендеринг.

Рекомендуемое разделение:

- hooks/features управляют состоянием и действиями;
- `dataSource` получает данные;
- `normalize` преобразует данные;
- компоненты отображают состояние и вызывают переданные actions;
- `renderer` постепенно заменяется React-компонентами расписания.

### Шаг 8. Перенести расписание и недельную навигацию

- Сначала перенести существующие функции парсинга и объединения месяцев в чистые TypeScript-функции.
- Добавить тесты на даты, понедельник недели, переход через месяц/год, пустые дни и несколько месяцев.
- Собрать компоненты `ScheduleView`, `WeekNavigation`, `DayCard`, `LessonCard`.
- Сохранить автоматический выбор ближайшей недели и прокрутку к текущему дню.
- Не менять формат отображения и порядок занятий в рамках миграции.

**Проверка:** одинаковый набор занятий и недель до и после миграции на одинаковых данных.

### Шаг 9. Перенести поиск и выбор сущностей

- Сделать переиспользуемые компоненты поиска и каскадных селекторов.
- Сохранить debounce поиска и ограничение числа результатов.
- Хранить выбранные значения в feature-состоянии, а сохранённые группы в storage-слое.
- Удалить прямое управление DOM через `querySelector`, `innerHTML`, `classList` из feature-логики.
- Для пустого каталога, неизвестного ID и устаревшей сохранённой группы показать корректное состояние.

### Шаг 10. Встроить API-точку расширения, но не API

- Создать `apiDataSource.ts` с тем же интерфейсом.
- На первом этапе оставить явную ошибку `NotImplemented` или заглушку, недоступную в production-конфигурации.
- Добавить конфигурацию `VITE_DATA_SOURCE=static|api` без секретов.
- Задокументировать, что токены/авторизация для API должны находиться на сервере или в безопасном прокси, если API нельзя вызывать анонимно.
- Когда API будет готово, реализовать только маппинг DTO API в доменные типы и интеграционные тесты; React-слой при этом не менять.

### Шаг 11. Обновить сборку и деплой

- Сначала проверить `npm run build` локально.
- Настроить GitHub Actions: установка Node-зависимостей, сборка Vite, запуск существующего Python-сборщика данных до сборки.
- Проверить копирование `data/` в итоговый `dist/`.
- Проверить `base` и загрузку приложения в GitHub Pages из подпути.
- Отдельно проверить Telegram Mini App на production URL.
- Не включать токены в Vite env-переменные, если они используются клиентом.

### Шаг 12. Удалить legacy-код после стабилизации

Legacy-код не удаляется. После стабилизации новой версии перенести его в отдельный каталог `legacy/`, сохранив возможность локального запуска и архивную копию прежнего интерфейса. Переносить только frontend entrypoint и связанные browser-файлы:

- `index.html`;
- `styles.css`;
- `logo.svg`;
- `js/`.

Общие `data/`, `scripts/`, `bot.py`, Docker-конфигурация и Python-зависимости остаются на уровне проекта. До переключения деплоя не менять расположение legacy-файлов, поскольку текущий workflow GitHub Pages использует корневой entrypoint.

Перенос выполнять только после того, как:

- новый интерфейс прошёл регрессионный чек-лист;
- статические данные загружаются в browser и Telegram;
- storage и офлайн-кэш совместимы;
- production build и GitHub Pages проверены;
- API-источник можно подключить заменой реализации, не меняя UI.

После переноса добавить `legacy/README.md` с командой запуска архивной версии и обновить workflow так, чтобы production-сайт собирался из `new/dist`.

## 6. Минимальные тесты

### Чистые функции

- разбор и нормализация занятия;
- объединение расписаний за несколько месяцев;
- получение недель из набора дней;
- выбор ближайшей недели;
- форматирование дат;
- построение плоского списка групп и преподавателей.

### Компоненты и сценарии

- загрузка студентов из статических JSON;
- загрузка преподавателей только при открытии вкладки;
- состояния loading/error/empty;
- выбор группы и преподавателя;
- поиск и выбор результата;
- сохранение и восстановление группы;
- fallback на кэш при недоступном источнике;
- browser без Telegram SDK;
- Telegram-тема и BackButton.

### Контракт источников

Один и тот же набор contract-тестов должен выполняться для `staticDataSource` и будущего `apiDataSource`: одинаковые доменные результаты, ошибки и поведение при отсутствии данных.

## 7. Порядок переключения источников

1. По умолчанию включён `static`.
2. Реализуется и тестируется API-модуль отдельно.
3. На staging включается API только конфигурацией.
4. Сравниваются каталоги, расписание, ошибки и latency со статическим источником.
5. После подтверждения API становится опциональным production-источником.
6. Статические JSON и Python-prefetch сохраняются как fallback до завершения периода наблюдения.

## 8. Критерии готовности миграции

- TypeScript-сборка проходит без ошибок.
- В production-клиенте нет токенов и секретов.
- Текущие JSON-файлы работают без изменения формата или через документированный адаптер.
- Все пользовательские сценарии из раздела 2 воспроизводимы.
- Поведение browser и Telegram сохранено.
- Пользовательские `localStorage`-данные не теряются.
- Источник данных меняется через конфигурацию/фабрику.
- Реализация API не требует изменений в React-компонентах и feature-логике.
- В CI проверяются typecheck, lint, тесты и production build.
